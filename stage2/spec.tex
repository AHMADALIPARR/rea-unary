\section{Human explanation}

\texttt{sample.bin} (22 bytes, SHA-256
\texttt{d5022462\ldots850}, verified on disk) is flat raw x86-32 machine code.
Its first instruction, bytes \texttt{01 D8} at file offset \texttt{0x00}, is
\texttt{ADD EAX, EBX}: add the 32-bit contents of EBX to EAX, store the
32-bit result back in EAX, and update the six arithmetic flags. The addition
is wraparound modulo $2^{32}$; any carry out of bit 31 is discarded from the
stored result but reported in CF.

The rest of the program is a signed 32-bit threshold predicate on that sum:
\texttt{CMP EAX, 10} sets flags from $EAX - 10$ (result discarded);
\texttt{JLE} branches to the \texttt{MOV EAX, 0} block when the sum is
$\le 10$ (signed), else \texttt{MOV EAX, 1}; \texttt{MOV EBX, EAX} copies the
0/1 outcome; \texttt{RET} returns. Net behavior:
$EAX = ((EAX_{in} + EBX_{in}) \bmod 2^{32} > 10) \,?\, 1 : 0$, $EBX = EAX$.
This document formalizes the \texttt{ADD} core; the control-flow context is
behavioral background for it.

\section{Formal operations and types}

Types: $\mathrm{uint32}$ (32-bit unsigned), $\mathrm{bool}$ (1-bit).
Let $x, y : \mathrm{uint32}$ be the operand values (EBX and the old EAX),
$s = x + y$ the full integer sum, $r = s \bmod 2^{32}$ the stored result,
and $carry_i$ the carry into bit $i$ with $carry_0 = 0$.

The core operation is
\[
\operatorname{addmod}(x, y, 2^{32}) = (x + y) \bmod 2^{32},
\]
with per-bit ripple structure
$r_i = x_i \oplus y_i \oplus carry_i$ and
$carry_{i+1} = (x_i \land y_i) \lor (x_i \land carry_i) \lor (y_i \land carry_i)$.

\section{Flag equations}

\begin{align*}
CF &= carry_{32} && \text{carry-out of bit 31} \\
PF &= \lnot (r_0 \oplus r_1 \oplus \cdots \oplus r_7)
    && \text{1 iff $r[7{:}0]$ has even parity} \\
AF &= carry_{4} && \text{carry-out of bit 3} \\
ZF &= \bigwedge_{i=0}^{31} \lnot r_i && \text{1 iff $r = 0$} \\
SF &= r_{31} && \text{sign bit} \\
OF &= carry_{31} \oplus carry_{32} && \text{signed overflow}
\end{align*}

\section{Control flow of the recovered program}

Four basic blocks: BB1 (\texttt{ADD}, \texttt{CMP}, \texttt{JLE}) branches to
BB3 (\texttt{MOV EAX, 0}) when $ZF = 1 \lor (SF \ne OF)$, else falls through
to BB2 (\texttt{MOV EAX, 1}, \texttt{JMP}); BB2 and BB3 join at BB4
(\texttt{MOV EBX, EAX}, \texttt{RET}). The \texttt{ADD}'s own flags are
overwritten by the \texttt{CMP} before the branch, so the branch tests the
comparison, not the addition.

\begin{itemize}
\item[A1.] 32-bit x86 execution mode; flat raw code, load base \texttt{0x401020}.
\item[A2.] mod-$2^{32}$ wraparound arithmetic per $\addmod{x}{y}{2^{32}}$;
  flags derive from the full unwrapped sum.
\item[A3.] Standard Intel x86 ADD flag semantics (Section~3). Documented
  architecture semantics, not invention.
\item[A4.] Unary-Boolean foundation: every 1-bit combinational node is one of
  const-0 / identity / NOT / const-1; multi-input fan-in is structural wiring

\item[A6.] Mandated state decomposition FETCH, DECODE, EXECUTE, WRITEBACK;

\item[A7.] ADD-core scope: this spec covers offsets \texttt{0x00}--\texttt{0x01}
  (\texttt{01 D8}); the rest is behavioral context.
